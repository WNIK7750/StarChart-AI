## 1. 复审目的与判定方法

本轮不重复罗列前序结论，而是执行两类反向验证：

1. 对已发现问题逐项回测，区分“确认、缩小、关闭、误报”；
2. 对前序未发现问题的领域提高审计权重，重点寻找被正向测试掩盖的边界缺陷。

判定状态：

| 状态 | 含义 |
| --- | --- |
| 确认 | 当前代码、运行探针或自动化测试可重复证明问题存在 |
| 确认并扩展 | 原问题成立，且发现额外影响或攻击路径 |
| 缩小 | 原方向成立，但数量、适用范围或严重度需要收窄 |
| 关闭 | 当前证据已证明原缺口消失 |
| 未验证 | 本地环境无法替代真实生产、网络、合规或容量证据 |

所有 Python 回归均在禁用 `dotenv.load_dotenv` 的进程内执行；本轮未读取真实 `.env`。

## 2. 加权审计策略

此前结论为正向的领域不再只做一次静态浏览，而是提高到 1.5～2.0 倍权重：

| 审计域 | 权重 | 增强检查 |
| --- | ---: | --- |
| 模块所有权与依赖方向 | 2.0 | 反向导入扫描、Router SQL 扫描、依赖注入检查 |
| 用户隔离、权限与隐私 | 2.0 | 跨用户访问、删除/恢复、导出再认证、审计脱敏 |
| Agent/Provider 数据边界 | 2.0 | 最小上下文、敏感输入阻断、Provider 配置拒绝、确定性回退 |
| 数据库迁移与资源生命周期 | 2.0 | 新库初始化、checksum、外键、完整性、文件句柄释放 |
| 前端输出与链接安全 | 1.5 | 动态 HTML 汇点、转义、URL 协议、opener、令牌存储 |
| 性能与退化 | 1.5 | Agent、Learning、Users 本地基线与预算回归 |
| 既有问题回测 | 1.0 | 按原攻击路径和配置组合复现 |

#### AUD-SEC-001A：安全问题仍是独立密码恢复因子

回测链路：

```text
start 返回问题
  -> verify 仅验证问题答案
  -> 签发 reset token
  -> confirm 设置新密码并撤销已有会话
```

限流、答案哈希、挑战令牌和会话撤销均有效，但不能把可猜测的知识问答提升为可靠认证器。该问题必须改为外部已验证通道的一次性恢复凭据，安全问题最多作为附加信号。

#### AUD-SEC-001B：密码找回接口可枚举账号

这是本轮新增的 P1 子项。不存在账号与存在账号的状态码、响应内容和业务路径不同。修复时应统一响应文案、状态和可观察时序，并增加“存在/不存在账号不可区分”的自动化契约。

#### AUD-SCA-001：依赖风险的正确解释

前序报告的“39 条公告记录”计数本身可复现，但应按根因和项目适用性归并：

- `python-multipart`：部分仅影响项目未使用的 API，但 multipart 头像上传路径仍命中适用的解析拒绝服务风险；
- `Pillow`：项目在实际格式校验前执行 `Image.open`，攻击者可用伪造 Content-Type 触发其他解码插件，不能仅按允许的目标格式排除公告；
- `Starlette`：项目实际挂载 StaticFiles，Range 解析风险适用；依赖 Host/request URL 的公告暂未证明可绕过授权，主要影响日志与请求分类；Windows UNC 风险仅在 Windows 生产部署时适用。

整改验收应保存“公告根因、适用路径、升级版本、回归用例”四列证据，而不是只追求扫描结果归零。

## 4. 高权重领域复审

### 4.1 架构边界：高置信通过

- 未发现 Agent 直接导入 Learning、Tools、Users repository；
- 未发现 Learning 导入 Users，也未发现 Learning/Tools/Users 反向依赖 Agent；
- Router 中未发现领域业务 SQL；`common.py` 的 `SELECT 1` 与迁移版本检查属于平台健康探针；
- `/users/me`、Agent 会话、长对话、聊天和工作流路由未发现缺失认证依赖；
- Users 命令安全矩阵覆盖 33 个命令，检查通过。

结论：模块化单体边界经反向扫描和运行时依赖检查后仍成立，置信度由“常规”提升为“高”。

### 4.2 用户隔离、隐私与 Agent 边界：高置信通过

以下 8 个高风险专项用例全部通过：

- 学习进度按用户隔离；
- 删除流程可恢复，且只匿名化目标用户；
- 数据导出要求重新认证且排除秘密字段；
- 审计 metadata 使用白名单并移除秘密；
- Agent 跨用户访问与资源不存在不可区分；
- 敏感用户输入不会进入 Provider；
- Agent Router 只传递最小用户上下文；
- 不安全或不完整 Provider 配置会被拒绝。

密钥模式扫描只命中测试中的伪造私钥和秘密形状 request id，未发现真实凭据。

### 4.3 数据库迁移：完整性通过，新增资源生命周期问题

在全新临时数据库上完成 20 个迁移：

- `PRAGMA integrity_check` 为 `ok`；
- 外键错误为 0；
- 46 张非内部表；
- 迁移 checksum 缺失为 0。

**AUD-DB-004 已整改**：`initialize_database()` 的启动连接已使用
`contextlib.closing` 显式关闭。Windows 回归确认函数返回后临时数据库可立即重命名、
重新打开做完整性检查并删除，不依赖 `gc.collect()`。

### 4.4 前端输出与链接安全：未发现新增 XSS，但纵深防御不足

- 共复核 55 个 `innerHTML`/`insertAdjacentHTML` 汇点；
- 安全问题、设置页会话/学习条目、Learning/Tools 动态内容均使用转义或安全 URL 适配；
- 未发现 `eval`、`new Function`、`document.write` 或 `postMessage`；
- 页面入口、URL 安全、错误反馈、Users 与 Learning 前端专项测试 19 项通过；
- 全量 Node 契约测试 31 项通过。

本轮没有确认新的 XSS 注入路径。但由于 CSP 缺失且 access token 位于 localStorage，一旦未来出现同源 XSS，影响仍然较高；AUD-WEB-002 与 AUD-AUTH-002 不能因此降级。

### 4.5 覆盖率：总体较强，边界层存在空洞

全量 159 个 Python 测试在分支覆盖模式下通过：

| 指标 | 结果 |
| --- | ---: |
| 后端语句 | 5605 |
| 未覆盖语句 | 757 |
| 分支 | 1214 |
| 部分分支 | 281 |
| 分支模式总覆盖率 | 84% |

强覆盖模块包括 Learning state repository 98%、schemas 97%、service 91%，Agent sessions 90%、service 94%、observability 92%，以及多数组 Users repository/service 83%～96%。

新增 **AUD-TEST-004（P2）**：安全和用户状态边界的 HTTP 集成覆盖偏低，主要包括：

- user_learning router：43%；
- privacy router：58%；
- learning router：59%；
- Users access/observability middleware：44%；

服务层高覆盖不能替代身份注入、状态码、响应脱敏、中间件记录和跨用户 HTTP 行为。应优先补齐上述边界，而不是把精力平均分配给已经超过 90% 的服务模块。

## 7. 整改与复验顺序

```text
第 1 批：统一且不可枚举的外部通道密码恢复
第 2 批：生产配置 fail-closed，尤其禁止 production 数据库重置
第 3 批：依赖升级、适用漏洞归并、头像/Range/表单拒绝服务回归
第 4 批：安全响应头、令牌暴露面、响应模型
第 5 批：CI 最小权限、Action SHA、SCA/Ruff/覆盖率门禁
第 6 批：补齐隐私/用户状态/中间件 HTTP 边界测试，关闭 DB 连接生命周期
第 7 批：真实 Provider、北京链路、容量、备份恢复和回滚签收
```

每批独立提交并独立复验。依赖升级、认证重构和生产配置收紧不应混在一个难以回滚的提交中。

## 8. 复审结论

前序审计的核心生产风险不是误报：三组原 P1 均成立，其中账户恢复新增账号枚举子风险；依赖公告数量需要按适用性收窄解释，但适用漏洞仍足以维持 P1。P2 基本全部复现，文档状态混乱问题已经关闭。覆盖率缺口从“没有数字”转化为“总体 84%，但安全边界 HTTP 层偏低”。

提高审计权重后，模块所有权、用户隔离、隐私删除/导出、Agent 最小上下文、Provider 输入阻断、迁移完整性和前端动态输出仍未发现破坏性反例，可信度显著提高；同时发现数据库初始化连接生命周期这一新的 P3 问题。

因此当前判定不变：

| 维度 | 判定 |
| --- | --- |
| 离线功能与回归 | 通过 |
| 架构边界 | 高置信通过 |
| 用户隔离与 Agent 隐私边界 | 高置信通过 |
| 本地数据完整性与性能退化 | 通过 |
