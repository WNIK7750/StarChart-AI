# 关键发现、风险与演进判断

## 1. 总体判断

项目的内部工程边界比普通课程型全栈项目成熟：领域所有权、迁移、幂等、隐私生命周期、Provider 失败回退和模型升级门禁都有实际实现。当前最大风险不是“缺少更多 AI 架构”，而是生产外部证据尚未完成，以及 7 月交接文档与 8 月代码之间出现了可见漂移。

## 2. 最重要的事实

### 2.1 Agent 是 grounded response composer

它更接近“基于站内证据的受控响应编排器”，而不是自主 Agent：

- 服务端选择能力；
- 服务端检索；
- 服务端拥有引用；
- 模型只重写答案；
- 服务端最终校验；
- 写入另走确认命令。

这个定位解释了为什么当前不需要 LangGraph、多 Agent 和向量数据库。

### 2.2 Deterministic 不是 mock

Deterministic 路径是：

- 无 Provider 时的正式产品能力；
- Provider 异常的降级结果；
- 离线测试基线；
- 卡片、引用和步骤的事实所有者。

删除它会同时损害可用性、安全和测试可复现性。

### 2.3 长期对话不等于长期记忆

长期对话是用户主动管理、最多三个、显式保存的历史。系统没有自动抽取用户画像、事实或偏好的长期记忆，也没有把长期对话自动注入所有未来对话。

## 3. 当前代码与文档的漂移

### F1：迁移数量漂移

当前事实：

- 数据库 22 个迁移；
- 文件存在 001–022；
- README、全栈交接和 2026-07-25 Agent 审计仍多处写 20。

影响：

- 旧证据仍可作为旧快照；
- 不能把其 migrationCount 当成当前发布证明；
- 新发布清单应以精确迁移文件集合和 checksum 为准。

### F2：测试数字漂移

旧 Agent 审计写 91 Python + 3 Node/SSE；当前静态测试源码已明显增加游客、HTTP、性能、生产覆盖层和快捷助手场景。

影响：

- 旧 gate passed 结论不覆盖当前工作树；
- 发布前需要生成新的完整 evidence snapshot；
- 不应手工改旧证据，应新增新版本证据。

### F3：Agent API 文档不全

当前代码新增或实际存在：

- `/agent/guest/chat`
- `/agent/sessions/draft`
- `/runtime/public`
- 快捷助手悬浮窗

早期 Agent 交接和 README API 列表未完整体现。

### F4：生产模板与安全启用顺序需要统一

`deploy/production/env.example` 目前写：

```text
STREAM_ENABLED=1
SESSIONS_ENABLED=1
PROVIDER=openai_compatible
LIVE_ENABLED=1
```

而多个发布文档要求：

```text
先以 deterministic / live=0 / stream=0 / sessions=0 发布
受控验证后按顺序开启
```

这可能代表“最终生产目标模板”和“首次安全发布档案”的不同用途，但模板本身容易被直接复制。正式部署前应明确：

- staging/dormant 文件允许哪些值；
- 首次启动安全值；
- 受控 Provider preview 值；
- go-live 值；
- 回滚值。

## 4. 需要特别关注的隐私边界

### F5：真实 Provider 实际会收到有界会话历史

代码事实：

- 登录会话会取最近最多 12 条、最多 12,000 字符；
- Orchestrator 把这些 `user/assistant` 历史加入 Provider messages；
- 历史经过秘密形状输入校验；
- 只有当前隐私政策同意有效时才允许 Provider。

部分 ADR/交接表述强调“当前问题 + 站内公开证据”，没有明确写“当前会话的有界历史也会发送”。这不是自动长期记忆，但仍是第三方处理的数据。

上线前必须让以下内容一致：

- 产品告知
- 隐私政策
- Provider DPA
- 数据流图
- 测试和日志边界
- 用户撤回同意后的行为

若产品不希望发送历史，应在代码中明确改为只发当前问题；若希望连续对话，应把历史范围写进正式告知。

### F6：最小 Users Context 不会原样发送给 Provider

代码中 Users Context 主要影响 deterministic 卡片排序和响应 meta。OpenAI-compatible request 只直接序列化：

- system instruction
- session history
- current user message
- site evidence

因此“允许发送最小偏好上下文”的文档说法比当前代码更宽。当前实现更保守，但文档应描述真实数据流，避免未来开发者误以为可直接发送完整 Context。

## 5. 运行与容量风险

### F7：进程内状态是明确的单 worker 约束

以下都在内存：

- Provider 并发和排队
- 用户/全局成本账本
- request replay
- single-flight
- 聚合指标

多 worker 会造成：

- 全局并发与成本上限被按进程放大；
- 相同 request ID 可能在不同进程重复调用；
- 指标分裂；
- 回滚判断困难。

配置已经 fail-closed 强制一个 worker，这是正确的。只有出现真实容量证据时才应替换 adapter。

### F8：SQLite 当前合理，但生产并发尚未证明

当前写路径已经使用事务、WAL、busy timeout 和 `BEGIN IMMEDIATE`。对当前体量合理。

触发迁移评估的信号应是：

- 生产写锁等待可复现；
- 会话/Users 写入 P95 超预算；
- 备份窗口不可接受；
- 多实例需求真实出现；
- 数据量和查询计划劣化。

不能仅因“企业级”提前换 PostgreSQL，但也不能用离线测试代替生产证据。

### F9：SSE 的“流式”有两种语义

当前有：

1. FakeProvider 可验证真实增量协议；
2. OpenAI-compatible Provider 只有完整回答；
3. 完整回答再按 80 字符投影成 SSE delta。

用户看到增量渲染，不代表模型 token 实时到达。运行快照已经用 `openAICompatibleIncremental=false` 表达这一点，产品/运维文档也应维持准确。

## 6. 安全设计评价

### 已有的强控制

- Provider host allowlist
- 不跟随 HTTP 重定向
- 输入秘密形状阻断
- 输出外链/域名/IP/HTML/秘密/伪引用阻断
- 有界输入、证据、输出和响应体
- 当前隐私同意门
- RBAC + ownership
- request ID 冲突检测
- 用户写命令确认 + 幂等 + 事务 + 审计
- 跨用户与不存在统一 404
- Refresh Token hash 与轮换
- 生产配置 fail-closed
- trace 不含用户或内容

### 仍需外部证明

- 供应商是否训练/留存
- 删除协助和分包商
- 北京地域与跨境边界
- 云侧费用硬限制
- 真实 API Key 最小权限和轮换
- 上海出站 allowlist
- DNS/TLS/代理链
- 真实取消和结算
- 生产备份权限与恢复

## 7. 产品和体验限制

### 规则意图路由

优点：稳定、低成本、可解释。

限制：多意图、同义表达、错别字和复杂语境可能落入 QA。

升级前应先观察：

- fallback 到 QA 的比例；
- 用户立即改写问题的比例；
- 不同意图的无结果率；
- pageContext 能否改善指代。

### 检索

当前是数据库/服务文本搜索与领域规则，不是向量检索。16 个学习节点和 144 条工具事实下足够轻量。

只有出现以下证据时再评估 embedding：

- 明确同义词召回缺口；
- 内容规模显著增长；
- 关键词扩展维护成本过高；
- 离线评测证明语义检索显著提升且没有引用/成本退化。

### 会话恢复

数据库只保存用户问题和最终答案。因此恢复历史时无法重新展示原卡片、引用、工具轨迹和工作流草案。

这是数据最小化的结果。若用户真实需要“历史回答保持完整可交互”，应单独设计：

- 哪些结构字段值得保存；
- 链接失效后的处理；
- 内容版本与历史展示；
- 导出和删除；
- 数据体量；
- 是否仍不保存 Provider 原始载荷。

## 8. 优先级建议

### P0：上线前必须完成

1. 完成 ICP 和公开条款/联系方式；
2. 完成 Provider DPA、留存、训练、地域和分包商签收；
3. 明确会话历史发送范围；
4. 设置云侧费用硬限制和告警；
5. 完成上海→北京 DNS/TLS/allowlist/延迟/容量验证；
6. 配置真实恢复发送端或明确禁用；
7. 生产备份、隔离恢复、回滚和值守演练；
8. 用当前工作树重新生成完整门禁证据。

### P1：发布材料一致性

1. 把 20 个迁移更新为 22 个当前事实；
2. 更新 API 清单：guest、draft、runtime public；
3. 明确生产 env 的安全初始档案；
4. 让快捷助手交付进入文档地图；
5. 区分“旧证据快照”和“当前证据”。

### P2：获得数据后再决定

1. 是否替换规则路由；
2. 是否增加向量检索；
3. 是否实现 Provider token 级流；
4. 是否保存历史结构化引用；
5. 是否引入共享治理状态；
6. 是否切换 PostgreSQL；
7. 是否增加第二 Provider；
8. 是否需要状态图或多 Agent。

## 9. 何时才应该引入 LangGraph / 多 Agent

至少要同时出现：

- 一个请求需要多个动态、可失败、可恢复的工具步骤；
- 步骤之间需要显式持久状态；
- 不同角色有明确独立目标和评测；
- 单编排器复杂度已经无法通过普通函数与状态 DTO 管理；
- 评测证明收益超过额外延迟、成本和安全面；
- 每个新节点都有关闭、回放、审计和降级路径。

当前项目还没有这些证据。现在引入只会把已经清晰的确定性链条变成更难验证的运行图。

## 10. 最终结论

当前最值得保留的架构资产是：

1. Learning / Tools / Users 的所有权边界；
2. deterministic grounding；
3. 模型只改 answer、不拥有引用；
4. 写入必须由用户确认；
5. Provider 失败不影响普通网站；
6. 幂等、会话、隐私和实验门禁；
7. 用证据触发复杂度，而不是预先堆叠 AI 框架。

如果这些边界继续保持，项目可以在不大改架构的情况下完成真实 Provider 上线；未来只有在真实流量与评测证明必要时，才逐步替换 Provider、检索或运行态 adapter。
