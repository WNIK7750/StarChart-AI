## 一、最终目标

关闭所有能够在当前本地工作区内可靠修复和验证的 P1、P2、P3 问题，并形成新的整改报告和机器可复核证据。

完成标准不是“代码看起来已经修改”，而是：

- 问题对应的攻击路径或失败配置先被测试稳定复现；
- 修复后原测试转为通过；
- 相关模块回归和全量门禁通过；
- 不破坏既有模块所有权、用户隔离、隐私和 Agent 数据边界；
- 文档、配置模板、CI、脚本和实际行为一致；
- 对必须依赖真实 Provider、生产网络、云资源或合规确认的事项，明确标为外部阻塞，不伪造通过证据。

## 二、工作区保护规则

当前工作区包含大量尚未提交的用户开发成果和文档迁移结果。开始前必须保存：

```powershell

```

必须遵守：

- 不执行 `git reset --hard`、`git checkout --`、`git clean` 或其他覆盖现有改动的操作；
- 不删除或回滚不属于本次整改的用户改动；
- 发现重叠改动时，先理解当前实现，再做最小范围补丁；
- 不读取、打印、复制、修改或提交真实 `.env`；
- 配置测试只允许读取 `.env.example` 和 `backend/app/core/config.py`，或在隔离进程中模拟环境变量；
- 不把真实密钥、用户数据、Provider 请求正文或响应正文写入测试、日志和证据；
- 不擅自创建提交、推送分支或发起 PR，除非用户明确要求；
- 每批整改保持可独立审阅、独立验证和独立回滚。

## 三、必须保持的架构边界

以下边界已经经过高权重复审，修复过程中不得破坏：

- Learning 保持用户无关，只负责公共学习内容；
- Users 拥有学习进度、活动、收藏、最近阅读、导入、隐私和用户资产；
- Agent 只能通过公开服务或薄工具访问 Learning、Tools、Users，不得直接导入其 repository；
- Router 保持薄层，不放领域 SQL 和复杂业务规则；
- Provider 不可用时，公共 Learning、Tools、Users 和确定性 Agent 能力仍应可用；
- Provider 只接收经过最小化和敏感信息过滤的用户上下文；
- 用户隔离、跨用户访问不可区分、删除可恢复、导出再认证和审计字段白名单必须继续成立；
- 当前模块化单体、SQLite、单 Worker 是有意的体量选择，不要借整改引入微服务、Redis、向量库、多 Agent 或状态图。

## 四、执行顺序

严格按下面批次执行。每一批都要经历：

```text
读取当前实现
  -> 编写或确认失败回归
  -> 实施最小修复
  -> 运行专项测试
  -> 运行受影响模块门禁
  -> 记录变更、证据和剩余风险
```

### 第 1 批：账户恢复与账号枚举（P1）

处理：

- `AUD-SEC-001A`：安全问题可独立完成密码重置；
- `AUD-SEC-001B`：密码找回接口可枚举账号。

要求：

1. 先增加测试，证明当前存在以下问题：
   - 只凭安全问题答案即可获得重置权限；
   - 存在账号与不存在账号的状态码、响应结构或可观察业务路径不同。
2. 将密码恢复改成外部已验证通道的一次性恢复凭据：
   - 使用密码学安全随机数；
   - 服务端只存哈希；
   - 绑定用户、用途、过期时间和单次使用状态；
   - 使用后立即作废；
   - 过期、重放、篡改和跨用户使用必须失败；
   - 成功重置后撤销全部会话；
   - 不记录原始令牌。
3. start 接口必须对账号存在与否返回统一状态、统一公开结构和近似处理路径。
4. 安全问题不得继续作为独立恢复因子；如为了迁移暂时保留，只能作为附加信号。
5. 如果项目没有邮件、短信或其他外部验证通道：
   - 不得伪造邮件已发送；
   - 先实现独立的恢复令牌领域接口与可替换发送端口；
   - 默认生产配置必须 fail-closed；
   - 测试使用内存 Fake sender；
   - 将“选择并接入真实发送服务”记录为明确外部阻塞。
6. 保持现有 API 兼容性时，旧安全问题接口可以进入明确的弃用流程，但生产环境不得继续通过它完成密码重置。

必须覆盖：

- 存在/不存在账号的公开响应不可区分；
- 令牌单次使用、过期、重放、篡改、跨用户失败；
- 重置后全部会话失效；
- 限流与审计事件仍有效；
- 日志和审计不出现令牌、答案或新密码。

### 第 3 批：依赖与输入处理（P1）

处理 `AUD-SCA-001`。

要求：

1. 重新运行 `pip-audit`，按“公告根因、是否适用、实际调用路径、修复版本、回归测试”归并结果。
2. 在独立改动中升级兼容的 FastAPI/Starlette、python-multipart 和 Pillow。

4. 头像处理必须：

7. 保存去重后的依赖审计结果，不得继续把公告记录数直接描述为可利用漏洞数。

### 第 4 批：Web、令牌和响应契约（P2）

处理：

- `AUD-WEB-002`；
- `AUD-AUTH-002`；
- `AUD-API-002`。

安全响应头：

- 为 HTML 与 API 增加 `X-Content-Type-Options: nosniff`；
- 增加适合当前静态页面结构的 CSP，避免直接使用宽泛 `unsafe-eval`；
- 增加 `Referrer-Policy`、点击劫持防护和合理的 `Permissions-Policy`；
- HSTS 只在确认 HTTPS 的生产环境启用；
- 对 `/`、API、错误响应和静态资源编写响应头契约测试。

Access Token：

- 优先改成内存中的短时 access token，并继续使用 HttpOnly、Secure、SameSite refresh cookie；
- 页面刷新后的认证恢复应通过 refresh 流程，而不是持久化 access token；
- 迁移时清理旧 `ai_nav_access_token` localStorage 值；
- 不破坏“写请求不自动重放”和 refresh token family 重放撤销；
- 如果当前架构无法一次完成迁移，至少先上严格 CSP、缩短 token 生命周期并形成清晰的临时风险记录，但不要把 AUD-AUTH-002 标记为已关闭。

响应模型：

- 先从 Auth、Users、隐私、Agent 写接口和错误敏感接口补齐；
- Router 只引用所属领域 schema，不复制 service 业务规则；
- 保持现有稳定错误码和前端 DTO；
- 每批比较 OpenAPI 快照，防止无意破坏客户端契约；
- 目标是让所有 JSON 业务操作有明确输出验证；确实不适用的流式、文件或空响应需书面说明。

### 第 5 批：CI 与质量门禁（P2）

处理：

- `AUD-CI-002`；
- `AUD-CI-003`。

要求：

- GitHub Actions 顶层声明最小 `permissions`，默认 `contents: read`；
- 将第三方 Action 固定到完整提交 SHA，并保留版本注释；
- 增加 Ruff 核心规则、`pip-audit` 和分支覆盖率门禁；
- 先以当前 84% 分支模式总覆盖率为基线，设置不会立即制造噪声、但禁止下降的阈值；
- 覆盖率和审计产物不得包含秘密或真实用户数据；
- 保持 Windows + Python 3.12 主门禁；
- 不要一次引入大量未经治理的类型或安全扫描噪声。若增加新扫描器，先建立基线和明确的失败策略。

### 第 6 批：边界测试、Ruff、数据库连接和仓库卫生（P2/P3）

处理：

- `AUD-TEST-004`；
- `AUD-CODE-003`；
- `AUD-DB-004`；
- `AUD-REP-003`。

优先补齐 HTTP/ASGI 集成覆盖：

- privacy router；
- learning router；

- platform navigation。

测试重点：

- 跨用户访问不可区分；
- 状态码、稳定错误码和响应脱敏；
- 隐私导出、删除、撤销和重新认证；
- 中间件 request id、审计白名单与秘密移除；
- Provider 故障时公共内容仍可用。

工程修复：

- 修复当前 4 项 Ruff 核心错误，不使用无关大规模格式化；
- 为数据库初始化连接增加显式关闭；
- 在 Windows 上验证初始化函数返回后，临时数据库文件可立即重命名和删除，无需 `gc.collect()`；
- 检查发布包、备份脚本和 `.gitignore`，显式排除日志、前端副本、临时覆盖率文件、数据库临时文件和本地运行产物；
- 不为了行数指标机械拆分大文件；只有出现明确职责边界和稳定测试时才拆分。

### 第 7 批：外部生产签收

处理 `AUD-OPS-002`。

本批只能在拥有真实环境和明确授权时执行：

- C4G 或目标规格容量测试；

- 生产备份、恢复、回滚和告警演练。

如果缺少凭据、云环境、合规负责人或费用授权：

- 不读取或猜测密钥；
- 不发起付费或生产流量；
- 生成一份逐项签收清单，注明责任人、所需输入、执行命令、成功条件和回滚条件；
- 将本批标记为“外部阻塞/未验证”，不能标记为通过。
