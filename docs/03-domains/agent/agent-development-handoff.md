# Agent 开发交接与工作流程

更新时间：2026-07-25

## 1. 交接结论

Agent 开发可以从当前版本继续，但必须循序渐进。仓库已经具备可运行的确定性 Agent 地基，后续工作是在现有契约上接入真实模型和产品闭环，不重新拆分 Learning、Tools、Users，也不提前引入多 Agent、状态图或向量库。

新对话开始后，先阅读本文，再以代码和测试作为最终事实源。

## 2. 当前基线

已经具备：

- `POST /api/v1/agent/chat`：返回稳定的结构化回答、卡片、引用、工具调用记录和工作流草案。
- QA、站内导航、工具推荐、学习计划和工作流建议等确定性意图。
- 通过公开服务读取 Learning、Tools 和 Users 最小上下文，不直接查询领域表。
- 输出守卫会过滤站外链接和无效引用。
- Provider 不可用时仍能使用 `deterministic` 模式。
- OpenAI-compatible Provider 边界、fake、配置/隐私/成本保护和关闭开关；真实流量仍未授权。
- JSON 与缓冲式 SSE 共用同一标准响应，助手页支持停止生成。
- 默认关闭的短期会话后端：显式创建、分页、恢复、删除、用户隔离、30 天到期清理、改标题和多置顶排序。
- 最多三个的长期对话：从短期会话原子升级、继续对话、改标题、置顶、删除、用户数据导出与最终匿名化清理。
- 助手页短期与长期会话交互、人工断线重试、停止、错误恢复和移动端抽屉。
- `POST /api/v1/agent/workflows/save`：经过登录授权、用户确认、幂等和审计后保存到 Users Assets。
- 独立助手页面 `frontend/assistant.html` 及对应脚本和样式。
- 版本化评估、盲评协议、脱敏 trace、运行指标、模型升级门禁和单 worker 拓扑保护。
- Chromium、Firefox、WebKit、Opera、真实移动设备和 Windows Narrator 验收。
- 专项验证入口 `scripts/verify-agent.ps1`，以及项目总门禁 `scripts/verify-foundation.ps1`。

上线前仍需完成：

- 真实 Provider 上线参数、供应商协议核对和受控联网验证。
- 上海服务器出站允许列表、真实容量、供应商侧费用硬限制和生产密钥轮换。
- OpenAI-compatible Provider 的真实增量结束事件、取消结算、用量字段与错误分类验证。
- 生产配置注入后的 CORS、Cookie、限流、日志脱敏、功能开关和回滚复核。

不属于当前欠账：长期记忆、跨进程状态、第二 Provider、向量检索、状态图和多 Agent 只在评测或规模阈值满足后另行立项。长期对话是用户明确管理的持久会话，不等同于自动长期记忆。

## 3. 必须保持的边界

```text
Agent API
  -> Agent 编排
      -> Provider
      -> Learning 公开读取能力
      -> Tools 公开读取能力
      -> Users Context 读取能力
      -> Users Command 确认写入能力
      -> 输出校验
```

- Agent 负责提示、模型调用、工具选择、上下文预算、引用组装和输出校验。
- Learning 负责路线、节点、资料和学习规则。
- Tools 负责工具事实、分类、搜索和链接状态。
- Users 负责身份、权限、偏好、学习状态、用户资产、隐私同意和审计。
- Agent 不直接写业务表，不复制领域 SQL，不让模型输出直接成为写命令。
- 所有用户写入必须经过显式确认、权限检查、幂等键、事务和审计。
- 现有确定性结果是离线回退和测试基准，不得在接入模型时删除。

## 4. 渐进工作流程

### 阶段 0：确认基线

1. 运行 `scripts/verify-foundation.ps1` 和 `scripts/verify-agent.ps1`。
2. 阅读 `backend/app/agent/`、Agent API 路由和现有测试。
3. 确认普通首页、学习区、工具区和用户空间不依赖 Agent 可用性。

完成条件：两套验证通过，当前行为和未实现范围已记录。

### 阶段 1：真实模型只读闭环

1. 在 Agent 模块内增加可注入 Provider 接口、fake provider 和一个真实实现。
2. 完成配置校验、超时、有限重试、取消、错误归类和密钥保护。
3. 保持“站内检索 -> 模型组织回答 -> 输出校验”的单一流程。
4. 不改变现有 `AgentStructuredResponse`；新增字段采用兼容方式。
5. Provider 未配置、失败或输出不合格时明确回退确定性模式。
6. 增加 QA、导航、推荐、学习计划、空结果、注入和越权测试。

完成条件：真实模型只能基于站内证据回答，引用可追溯，失败可回退；不新增会话、长期记忆或多 Agent。

### 阶段 2：流式输出与短期会话

1. 让完整 JSON 与 SSE 共用同一套编排和事件模型。
2. 增加停止、超时、断线恢复和前端增量渲染。
3. 使用追加迁移保存最小会话和消息，覆盖用户隔离、分页和删除。
4. 为流式和会话分别设置开关，关闭后回到阶段 1。

完成条件：流式与完整回答语义一致，取消后不继续写入，用户只能访问自己的会话。

### 阶段 3：经确认的用户闭环

1. 先完善工作流草案的预览、修改、确认和保存体验。
2. 根据实际需求每次只增加一类写能力，例如收藏或学习计划保存。
3. 所有命令继续通过 Users Command，覆盖重复提交、并发冲突和权限撤销。
4. 长期记忆保持关闭，直到同意、删除、导出和质量验证全部具备。

完成条件：模型不能自行写入；失败可恢复，重试不会生成重复数据。

### 阶段 4：质量与运行治理

1. 建立版本化评估集和发布阈值。
2. 记录 request ID、模式、Provider、Prompt 版本、工具、耗时、成本、回退和校验错误。
3. 对日志和评估数据脱敏。
4. 只有评估证明确有必要时，才考虑第二 Provider、向量检索、状态图或多 Agent。

完成条件：评估可在本地和 CI 重复执行，安全与越权样例零放行，每个复杂组件都有关闭和回退路径。

### 阶段 5：体验与发布收口

1. 完善助手页的会话、停止、重试、引用、确认和错误恢复。
2. 完成键盘、焦点、读屏、长文本、窄屏和 reduced motion 验收。
3. 覆盖 Chromium、Firefox、WebKit、Opera 和至少一种真实移动设备。
4. 执行 Agent、Foundation、迁移、备份恢复、安全、性能和链接总门禁。
5. 验证生产密钥、CORS、Cookie、限流、日志脱敏和功能开关。

完成条件：Provider 故障或 Agent 关闭时普通网站功能不受影响，并形成发布说明、已知限制和回滚记录。

## 5. 当前下一任务

离线开发、体验与门禁已经完成。当前只保留以下上线任务：

1. 【上线前处理】核对供应商协议、费用限制和留存策略；使用百炼默认业务空间、北京专属域名及上海服务器出站 IP 白名单完成受控真实验证。
2. 在上海生产主机验证真实容量、取消/结算/用量字段、Provider 结束事件和错误分类，升级模型比例继续为 `0%`。
3. 注入生产密钥后复核 CORS、Cookie、限流、日志脱敏、功能开关、备份、回滚与完整门禁。

实时 Provider 继续保持关闭；上海服务器无需迁移北京，无法创建额外业务空间不阻塞上线准备。长期记忆、LangGraph、多 Agent、向量库、共享状态和 DeepSeek 运行依赖均不是当前版本的未完成任务。

### 2026-07-23 / 安全增量 SSE 与背压

用户可见结果：支持增量协议的 Provider 可逐块显示回答；不支持的 Provider 继续使用现有安全缓冲模式，JSON 行为不变。真实 Provider 和流式总开关仍默认关闭。

契约边界：新增可选 Provider 增量事件协议。每个累计前缀在进入 SSE 前执行与最终回答相同的外链、密钥样式、HTML、引用和长度守卫；后续块失败时停止继续暴露并以最终确定性响应覆盖。生产与网络消费之间使用 `AI_NAV_AGENT_STREAM_BUFFER_EVENTS=8` 有界队列，可配置范围 1 至 64；慢客户端暂停生产，流关闭取消 Provider。

验证与结果：52 项 Agent Python 测试通过，新增覆盖真实 fake 增量顺序、恶意后续块阻断、最终响应一致、有界队列背压与流关闭取消；相关 Node SSE/前端契约和格式检查通过。

### 2026-07-23 / 断线后的人工重试与完成响应重放

用户可见结果：首次发送即生成稳定的 `X-Request-Id`。连接中断、超时或 502/503/504 时不自动重发，只显示“重新发送”和费用风险说明；用户确认后复用原问题、原会话与同一请求标识，不重复插入用户消息。主动停止、401、409 和 422 不提供重试操作。

契约边界：完整生成且可选会话写入成功后，标准 `AgentStructuredResponse` 才进入进程内重放缓存；默认 TTL 为 `AI_NAV_AGENT_RESPONSE_REPLAY_TTL_SECONDS=300`，最多 `AI_NAV_AGENT_RESPONSE_REPLAY_MAX_ENTRIES=512`。命中时不再次调用 Provider；同一用户重复使用请求标识但内容指纹不同返回 `409 AGENT_REQUEST_ID_CONFLICT`。缓存不保存 Provider 原始响应、提示词、密钥或完整用户上下文，取消和失败结果不缓存。

验证与结果：58 项 Agent Python 测试通过，其中新增覆盖防御性副本、过期、LRU 容量、内容冲突、完成响应只调用一次模型及取消不缓存；Node 前端/SSE 契约与 JavaScript 语法通过。Playwright Core 模拟流式回答中断后人工重试，两次请求标识一致、用户消息始终一条、成功后重试操作消失且控制台无错误。Browser 插件不可用，按前端测试技能使用 Playwright Core 回退。

运行边界与回滚：该缓存与现有阶段 1 治理账本一样只适用于单 API worker，不跨进程或主机。当前部署继续保持单 worker；最终多实例上线前替换为带 TTL 的共享幂等存储。删除 `X-Request-Id` 重放接入并保留人工重试 UI 即可回滚缓存，不涉及数据库迁移。

剩余风险：如果请求在服务端真正完成前被取消，人工重试会产生一次新的 Provider 调用；若已完成并写入缓存，则直接重放。浏览器无法证明最终供应商计费行为，真实 Provider 的请求终止、用量结算和多实例幂等仍属于最终上线验证。

下一任务：继续离线评估默认模型升级必要性与 Agent 运行观测边界；真实 Provider、共享幂等存储和北京端点/上海出站配置保持上线前任务。
