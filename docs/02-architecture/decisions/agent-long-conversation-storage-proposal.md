# 长期对话存储方案

状态：2026-07-25 已确认并实现。

## 推荐方案

阶段 1 继续使用当前模块化单体和 SQLite，在 Agent 模块内建立独立的长期对话表与消息表。短期会话仍是默认 30 天到期的缓存；长期对话不设置自动到期时间，由用户主动删除。

该方案成本最低，支持登录后的跨设备读取、统一备份恢复和用户数据删除，也不需要新增 Redis、对象存储或微服务。

## 数据边界

- 长期对话表保存：用户、显示标题、置顶时间、来源短期会话、创建与更新时间。
- 长期消息表只保存：用户问题、最终通过校验的助手回答、角色、时间，以及用于防止重试重复写入的有界请求标识；请求标识不向页面返回。
- 不保存：Provider 原始请求或响应、系统提示、API Key、完整 Users Context、内部工具参数、推理过程。
- 长期对话和消息继续归用户所有，跨用户访问与不存在保持相同的 404 行为。

## 升级事务

建议使用一个原子“升级”命令：

1. 校验登录用户拥有所选短期会话。
2. 校验会话至少完成一轮问答，且没有正在生成的请求。
3. 校验长期对话配额。
4. 在同一数据库事务内复制会话与消息，并记录来源短期会话。
5. 升级成功后从短期区移除原记录；任一步失败则完整保留短期会话。
6. 使用幂等键避免重复点击生成两份长期对话。

侧边栏在“短期会话”上方增加“长期对话”分区。两个分区各自排序；长期对话复用修改标题、置顶、取消置顶与删除能力。

## 暂不采用

- 浏览器 IndexedDB：不能可靠支持跨设备、统一备份和账号删除。
- Redis：适合高并发临时缓存，不适合作为长期记录的唯一存储，当前体量也不需要。
- 数据库索引加对象存储：只有出现大量附件或超长历史后才有收益，阶段 1 会增加不必要的运维复杂度。

## 已确认决策

1. 每个用户最多拥有三个长期对话；删除长期对话后可重新升级其他短期会话。
2. 升级成功后从短期区移除原会话并显示在长期区，不保留重复记录；升级失败时短期会话保持不变。
