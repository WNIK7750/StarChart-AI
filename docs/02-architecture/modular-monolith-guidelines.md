# 模块化单体架构规范

## 1. 适用范围

本项目采用小型企业级模块化单体：一个 FastAPI 应用、一个部署单元、一个 SQLite
数据库和一套版本迁移。模块用于管理业务所有权和代码依赖，不是可独立部署的微服务。

目标是在当前项目体量下获得清晰边界、可测试性和可维护性，同时避免分布式系统成本和
形式化分层。

## 2. 顶层模块

只保留以下稳定业务模块：

| 模块 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Learning | 路线、节点、资料、章节、学习规则 | 用户进度、收藏、Agent 编排 |
| Tools | 工具事实、分类、集合、搜索和链接状态 | 用户收藏、页面静态副本 |
| Users | 身份、私有状态、偏好、资产和隐私 | 学习/工具公共事实、模型推理 |
| Agent | 对话、模型调用、工具编排和引用组装 | 直接访问领域表、拥有业务事实 |
| Platform | 配置、数据库、迁移、日志、健康检查 | 领域业务规则 |

模块都在同一进程内直接调用公开 Python API。禁止仅为形式上的边界引入内部 HTTP、消息队列、
事件总线或分布式事务。

## 3. Users 内部功能组

Users 体量较大，可按内聚功能分为五组，但这些组不是微服务：

1. **Identity**：注册、登录、账号、安全、会话和授权。
2. **Settings**：资料、头像和偏好。
3. **Learning state**：进度、活动、最近阅读、继续学习和收藏。
4. **Assets**：保存的工作流和后续用户资产。
5. **Governance**：隐私、审计、命令安全和用户侧观测。

同组功能优先共享 service、repository 和事务边界。只有安全模型、数据生命周期或复杂度
明显不同，才保留独立子包。

## 4. 默认代码深度

新模块默认从最小结构开始：

```text
module/
  service.py       # 用例和业务规则
  repository.py    # 查询、持久化和 SQLite 事务
  schemas.py       # 仅在 DTO 较多时增加
```

HTTP router 保留在统一 API 层。单一 SQLite 实现时，repository protocol 与实现可放在同一
文件；不能因为“未来可能替换数据库”提前创建 port 和 adapter 目录。

满足以下至少一项时才增加独立抽象：

- 已经存在两个真实实现，而不是假设未来可能存在。
- 外部系统边界需要隔离，例如模型 provider 或对象存储。
- 业务策略复杂且需要独立单元测试或复用。
- 文件职责已经难以说明，或多个开发者会长期并行修改。

Facade 只用于跨模块公开 API，不用于包装同模块中的单个 service 调用。Policy 只承载可复用
决策规则，不作为简单条件判断的固定目录。

## 5. 依赖规则

- Router 处理 HTTP；service 处理用例；repository 处理 SQL 和事务。
- 同一模块内部可以直接调用，不为每次函数调用增加接口层。
- 跨模块只依赖对方公开 service/facade，不导入 repository 或数据表细节。
- Agent 只能调用 Learning、Tools、Users 的公开能力。
- 公共工具代码必须确实被至少两个模块使用，否则留在所属模块内。
- 数据库共享不等于所有权共享；每张业务表只有一个模块负责写入。

## 6. 演进策略

- 不对已通过验收的 Users 代码做一次性目录搬迁。
- 修改相关功能时，顺手合并仅有一个实现、只做转发的 port/facade。
- Tools 先建设一个内聚模块，不拆成 catalog/category/collection/link 等子服务。
- Agent 先完成一个可用纵向链路，再根据模型 provider 或会话复杂度提取接口。
- 以用户可见功能和数据一致性为交付单位，不以新增包、接口或抽象数量衡量进度。

## 7. 评审检查

每次新增目录或抽象前回答：

1. 它是否对应稳定业务所有权，而不只是一个页面或一张表？
2. 当前是否有两个真实调用方或实现需要这个边界？
3. 不增加这层是否会导致业务规则重复、事务失控或跨模块耦合？
4. 新层带来的测试和理解成本是否低于它消除的复杂度？

任一答案不明确时，先使用模块内直接实现。
